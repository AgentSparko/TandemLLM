# Reference: metrics and the usage ledger

## Prometheus metrics

`GET /metrics` serves the families below in the Prometheus text format, to anyone while no token is set, else behind the metrics or admin token, or to a request from the machine itself. `ops/monitoring/` has a scrape configuration, alert rules with their tests, and a Grafana dashboard generated by `tools/grafana_dashboard.py`. With the metrics token set, a scrape job needs it as a bearer token:

```
- job_name: tandemllm
  authorization: {type: Bearer, credentials_file: /etc/prometheus/tandem-metrics.token}
  static_configs: [{targets: ['gpu-host:8000']}]
```

The engine's families never count a relayed request. The table lists every family the engine registers with a literal name in the code; families built at scrape time from a table (the cache families by `cache` label) are listed by their prefix in the help text of the page itself. The extension's families (`qse_conductor_*`, marked `"owner": "ext"` in `contracts/engine-api-v1/metrics-families.json`), the proxy's and the host collector's are in [TandemApp's docs](https://github.com/TandemLLM/TandemApp/blob/main/docs/README.md).

## The usage ledger

`server/api/ledger.py` writes one SQLite row per request: counts, timings, the finish reason, the cache source, a client id. Never the prompt, the answer, a tool name or argument, a conversation id, the `user` field, an IP address or a raw token. Refused requests (503, 429) and rejected ones (400) are rows too, with null token fields, so the request count is honest.

It never slows or fails a request. A row is put on a bounded queue (10,000), a writer thread commits in batches at most every second, and a disk error drops that batch, counts it and logs it at most once a minute. Rows older than `--usage-retention-days` (at least 400) are deleted once a day, and once an ISO week an online backup goes beside the file, the newest 8 kept. The server takes the path from `--usage-ledger` only, never from the environment, so a benchmark server started with `serve.env` exported never writes the operator's ledger. Migrations are forward only and in place, and keep every row.

A row's speed figures follow the benchmark row's formula, and a replay or a side-lane request has no decode rate. A relayed request has null queue, prefill, blocks, draft counts and cache source unless a plugin reported them, in which case `l2_join` says how the row was joined. A quick look:

```sh
sqlite3 ~/.qwen38-spark-engine/usage/ledger.sqlite3 \
  "select datetime(ts_ms/1000,'unixepoch','localtime'), finish_reason, prompt_tokens,
          completion_tokens, round(decode_tps,1), cache_source from requests order by id desc limit 10"
```
