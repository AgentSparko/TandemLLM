    Parallel requests¶

    With --parallel N the engine holds N sequences (lanes) over the one copy of the weights and decodes up to N requests at once. Two or more decoding requests share each verify pass, so the weights are read once for all of them. The flag's own default is 1; the shipped ops/serve.env, the profiles of every family with side slots and the Setup Guide run 8 lanes (SRV-707), every lane with the same window, except ops/profiles/_ornith.env and _flint.env, which keep QSE_PARALLEL=1 (a setup through the guide writes the card's count over it, setup.md).

    How it works inside (slots, the GPU turn, lockstep rounds, admission) is in server.md, section Parallel requests. This page is about using it.

    Switching it on¶

    In ops/serve.env (or local.env):

    QSE_PARALLEL=8            # lanes: slot 0 and N - 1 side slots; 1 is one sequence
QSE_SIDE_MAX_LEN=0        # 0: every side slot has MAX_LEN, slot 0's window (a shorter value is kept)
QSE_KV_POOL=on            # windows are addresses, pages are committed as conversations grow
QSE_PARALLEL_FLOOR_GB=15  # admission keeps MemAvailable at or above this

    then restart the service. The same settings as flags: --parallel N, --side-max-len, --parallel-floor-gb.

    flag default what it does
    --parallel N 1 (serve.env: 8) sequence slots; N - 1 side slots beside the engine
    --side-max-len 0 a side slot's window; 0 is --max-len, every lane the same window (SRV-707). A shorter one is kept for old setups; a request whose prompt plus max_tokens does not fit it waits for slot 0
    --parallel-floor-gb 15 a request waits while what the caches may still grow into (at most the engine's room to --mem-peak-gib), the workspaces of the prefills in flight, its own and the KV pages still to commit would push MemAvailable under this, a request alone too (0.15.1, SRV-775); a side slot is built only if it fits above it. The wait is queue time (wait_mem_ms in the ledger) and the client sees a waiting line
    QSE_GUARD_MARGIN_GB 5 the floor a check holds is the live guard (SRV-785): one prefill chunk's workspace at the class of the longest prefill in flight, one KV commit, a chat sandbox's ask from the last minute and this margin, never above --parallel-floor-gb (for the KV pool's commits, never above QSE_KV_HARD_FLOOR_GB). The wait line names its inputs
    QSE_MEM_WAIT_S 10800 the longest a streamed request, or one that sends wait_for_memory: true, waits for memory (3 h); any other request without a stream waits at most --queue-timeout. Then it is refused with the reason: a 503 with Retry-After, or an error event (memory_wait_timeout) on a stream opened while it waited (SRV-787, SRV-797; Waiting for memory)
    QSE_PEAK_STRICT 0 1: a lone request the memory gate refuses waits too instead of running over the peak, and the gate counts the workspaces of the prefills in flight on the reserve (SRV-775; in no profile)
    QSE_REQ_PEAK 0 1: the [req] line adds peak_gib=, the allocator's peak over a request that ran alone less what was allocated at its prefill's start (a measurement, SRV-773)
    --parallel-batch on decoding slots verify their trees in one joint pass (off: they take turns)
    --parallel-draft on the decoding slots' draft calls in one packed pass over the drafter
    --parallel-cut the family's share: each slot's tree cut to a fixed share (16 rows at two slots, 10 at three, 8 at four); joint: the round cuts all trees together, best nodes first; auto (SPD-155): joint from QSE_PARALLEL_AUTO_N (3) decoding slots, share below. Unset, the model family's joint_policy decides (the 27B: auto), else share
    --parallel-draft-rows 128 rows of a packed draft pass (SPD-157): eight slots' 16-row draft blocks in one pass; drafting decides speed only
    --parallel-max-rows the family's rows of a joint pass at most (QSE_PARALLEL_MAX_ROWS; 0 or unset: the model family's joint_policy, else 32). SPD-159: the 27B on EXL3 weights takes 64, each engine's rows in an 8 x 8-row joint pass bit for bit its own eager verify; on NVFP4 and FP8 it keeps 32, since NVFP4 sends 33-64 rows to another tile; past max_rows // 2 decoding lanes (2 rows each) a round runs more passes
    --side-precapture off capture a side slot's verify graphs at start (about a minute a slot) instead of at first use
    --side-graphs on off: a side slot holds no verify graphs and verifies eager when it decodes alone (about 1.5 GiB instead of 7.5 beyond its window)
    --side-slot-const-gb 7.5, or 1.5 with side graphs off a side slot's bytes beyond its window in the build's estimate (QSE_SIDE_SLOT_CONST_GB)

    8 lanes are measured on the 27B, Flash-Next, Ornith and Flint (SRV-711, 2026-10-24, 1/2/4/8 requests at once, total tok/s, 3-round medians, N decoding at once: the 27B ThinkingCap EXL3 4.0 38.3 / 67.6 / 100.1 / 154.5, Flash-Next 3.05 36.5 / 45.6 / 57.5 / 71.3, Ornith EXL3 4.0 37.7 / 47.0 / 58.4 / 69.8, Flint EXL3 4.0 111.7 / 154.9 / 193.3 / 232.3). Every weight card has a speed row with 1, 2, 4 and 8 requests at once on the current build (measurement.md); a card's lanes default is never above the lanes its row measured.

    The shipped ops/serve.env runs 8 lanes on the pool with QSE_SIDE_GRAPHS=off and QSE_SIDE_SLOT_CONST_GB=1.5, the values the Setup Guide writes for the 27B. Until SRV-707 it kept one sequence, and the box the older measurements come from ran two with a 65,536-token side window.

    One window for every lane (SRV-707)¶

    Every lane has the window the setup names (MAX_LEN); the Setup Guide has no side window of its own any more, and writes QSE_SIDE_MAX_LEN equal to the window. With the KV pool on a lane's window is addresses: a side slot built at 262,144 tokens takes its constant part and nothing of its window at load (engine/models/*/serving.py side_slot_bytes: no bytes a token when paged), and its pages come from the one pool as its conversation grows. With the pool off (the families whose pool is not verified yet: NemotronH, LFM2.5, Flint, Ornith) every lane's window is memory at load, and a lane is built only while the floor holds.

    The guide counts how many lanes can all hold the full window at once, the guarantee (lanes_full in the estimate): min(lanes, floor(room / (window x KV bytes a token))), where room is what the budget leaves after the weights, the tools and every lane's constant part. With the pool off it is every lane whenever the selection fits. Past the guarantee the lanes share what is left, in this order:

    1. A new request waits for memory before its prefill (the admission reserves its prompt and up to QSE_KV_ADMIT_ROWS of its max_tokens in pages): its stream says "waiting: memory is almost full", the Lanes view and the live view show it as waiting_memory with what it needs, what is free, what is being freed or which prefill is in the way, and when the wait ends. A streamed chat request gets its stream's headers at once and an SSE comment every 15 s while it waits, so no client's read timeout cuts the wait; it waits up to QSE_MEM_WAIT_S (SRV-787). With the KV pool the admission checks two things, each as the pool's gate will see it, in the order the pages commit (SRV-797): the prompt's pages (and the router's notes' room) against the pool's hard floor while the prefill runs, without the request's own workspace (the 27B maps the prompt's rows before its prefill; Flash-Next maps each chunk's rows before that chunk and gives the allocator's blocks back after every chunk once the state holds more than 4,096 rows, and the pool's floor already holds one chunk's workspace); the whole request (workspace, every page) against the admission's floor, as before. So the pool never refuses a page the admission counted, and nothing is counted twice: a 142k turn with a 10.8 GiB workspace resumed in place is admitted at 19.9 GiB.
    2. A turn short only by the caches' room (what the state store and the resident prefix may still take under the memory policy's ceiling, which nothing holds) does not wait: it is let in on that room, which the policy keeps from the caches until its prefill has run, or until it ends when its answer's pages needed it too ([parallel] ... let in on N GiB of the caches' room). Only the shortfall is held: the caches still grow by the rest of their room, and a cache that would grow into the held part (a stash, another chat's guest rows, a state-store snapshot) is refused meanwhile, so that conversation may read more again on its next turn. The response cache's budget (host memory) stays counted.
    3. Before anyone waits for memory something holds, idle conversations give their pages back, as much as the admission is short and in this order, each level in the log with its bytes and ms: the caches' levels and the allocator's free blocks, the small models, idle side slots' conversations already current on the NVMe (the idle backfill wrote them: trimmed only), the others (oldest first, a turn that ended within 30 s last, each to the NVMe first with the spill on), slot 0's idle conversation (to the NVMe first unless current), then the side conversations no save could write (SRV-779), then the kept park; after it the host heap is trimmed (malloc_trim, at most every 30 s).
    4. A running lane whose next pages would take the box under QSE_KV_HARD_FLOOR_GB gives way (SRV-709, QSE_KV_RECOMPUTE=on), a streamed one in its prefill as in its answer and alone too (SRV-797): it gives every page back (its conversation to the NVMe first), waits at the head of the line for memory (before any request that has not started; among such lanes, the one that gave way first) and goes on in the same stream by reading its prompt and the text it wrote again. A streamed client sees an SSE comment (: paused: waiting for memory) meanwhile, no token. Each give-way with fewer than 256 tokens written since the one before backs off twice as long before it is admitted again (1 s, 2 s, 4 s, up to 60 s; : paused: backing off after giving way when memory is there), so a lane the pool keeps refusing does not read its rows back every few seconds; while it backs off, requests that fit go. Its re-admission is priced as its first (image rows, cache_prompt, its home slot, its priority), the request's --request-timeout does not count its waits (nor its first admission's), its waits for memory add up toward QSE_MEM_WAIT_S from its first admission on, and a planned stop during the wait ends it with the restart's retryable error (engine_restarting). /health parallel.recompute counts the lanes that gave way, resumed and gave up. Reading again costs a prefill; the text goes on where it stopped, and a sampled or near-tie token after the resume may differ from the one an uninterrupted run would write. The thinking budget goes on from where it was once the lane wrote a token; refused before that, it starts as it would have.
    5. A streamed lane stops only once its waits for memory add up to QSE_MEM_WAIT_S, with the wait's refusal (memory_wait_timeout). One not streamed (its client reads nothing until the answer is whole) keeps SRV-709's count: alone it stops at the pool's refusal with memory_full, beside other lanes it gives way at most KV_RECOMPUTE_MAX (16) times. What changed for it (SRV-797): each of those waits is now a non-streamed request's wait, at most --queue-timeout after a 1 s backoff, ending with memory_wait_timeout (a 503 to send again); before, each could last up to QSE_MEM_WAIT_S with nothing sent. The Chat tab keeps the text and continues it once memory is free.
    6. A request not streamed waits for memory at most --queue-timeout (120 s), then gets a 503 with Retry-After: 30 and the code memory_wait_timeout, its message naming the cause: "Memory stayed full for 2 min (needed X GiB, Y GiB free above the guard): this turn did not start; send it again, or stream it (or send wait_for_memory: true) to wait longer." A client that does not stream and wants the long wait (an agent app) asks for it with wait_for_memory: true in the body (or in its tandem object) or the header X-Tandem-Wait-For-Memory: 1: it then waits up to QSE_MEM_WAIT_S and gives way as a streamed one does.

    Admission reserves KV pages for the prompt and at most QSE_KV_ADMIT_ROWS (8,192) of max_tokens (0: all of it), so more lanes start than the worst case allows; a lane that writes past its reservation and finds the pool full gives way as above.

    A round with more than 16 decoding lanes verifies in more than one pass of 32 rows (2 rows a lane), so each lane gets less speculation; the guide says so above 16 and takes up to 64.

    Waiting for memory¶

    A request whose bytes do not fit above the floor waits for memory before its prefill. The server pauses it and does not refuse it: it keeps its place in the line, and its prefill starts by itself once memory frees. The client sends nothing again. This holds with more than one lane, where the admission by bytes runs (server/app.py _par_admit).

    What a client sees while it waits:

    • A streamed chat request gets its stream's headers at once, with X-Tandem-Wait: memory, and an SSE comment every 15 s: : waiting for memory, position <n>, <x> GiB short, <s> s so far, refused in <s> s unless memory frees. A comment is no event, so no client reads it as a token, and an idle-read timeout does not close the connection. With the profile's progress lines on, the client also gets a waiting line, "memory is almost full, your request starts when a running one frees memory".
    • The live view and the Lanes view show the request as waiting_memory, with activity.memory: need_gib (what this turn takes in the check that holds it), others_gib (what other turns and the caches hold, 0.15.4), check (request, prefill or peak, 0.15.4), rows (the rows it forwards), free_gib, guard_gib and its inputs guard, short_gib, freed_gib, in_the_way (the prefill in its way, with its time left), place, waited_ms, bound_s, ends_in_ms, and lines, the three sentences the dashboard shows (dashboard.md).
    • The engine log has [parallel] <id> waits for memory: ... with the check's terms, still waits for memory (<s> s of <bound>) every 15 s, and [parallel] <id> admitted after <s> s at the end. The ledger books the wait as wait_mem_ms. A wait does not count toward --request-timeout.

    The line for memory goes by the chat's priority, then by arrival (server/slots.py Admission.wait). The priority is tandem.priority in the request body: "high", "normal" or "low", and anything else or no field is normal. A request that waits moves up one step for every 30 minutes it has waited, so a low chat still gets its turn. A new request does not take the bytes a higher-priority waiter is held for: it joins the line behind it. The KV pool's reclaim takes the idle conversations of lower-priority chats first, after the older copies of a chat. A lane that gave its memory back in the middle of its answer goes to the head of the line. The Chat tab sets the priority per chat (chat.md).

    How long it waits:

    knob default what it does
    QSE_MEM_WAIT_S 10800 (3 h) the longest wait of a streamed request, or of one that asks for the long wait with wait_for_memory: true (in the body or in its tandem object) or X-Tandem-Wait-For-Memory: 1
    --queue-timeout 120 (serve.env: 240) the longest wait of any other request not streamed
    QSE_KV_ADMIT_ROWS 8192 the part of max_tokens the admission reserves KV pages for; 0 is all of it
    QSE_KV_RECOMPUTE on a lane the KV pool refuses gives way and goes on later; off ends it with memory_full

    The table in the section Switching it on above has the floors the wait checks against: --parallel-floor-gb, QSE_GUARD_MARGIN_GB and, for the pool's commits, QSE_KV_HARD_FLOOR_GB (10).

    At its bound the server checks the request once more and then refuses it: a 503 with Retry-After: 30, type server_busy, code memory_wait_timeout, and a message that says what it needed and what was free above the guard. A stream opened while it waited ends with the same error as an event. A planned stop ends the wait at once with a 503 to send again. A client that leaves while it waits is booked abandoned (left_while_waiting_memory).

    What a turn is charged (0.15.4, SRV-801)¶

    The admission reserves the workspace of the rows the prefill forwards and the KV pages its prompt may still commit. It counts the rows from where the prompt resumes on its slot: the rows in place, the end anchor, or the conversation's entry on the NVMe (ws_kind=spill, #167). The [req] line has the charge as ws_rows and ws_gib, and the rows forwarded as fwd.

    • Slot 0 counts its own conversation. On 0.15.3 slot 0 had no share of it, so a turn of the chat it held was charged a cold read of the whole chat. On a user's box such a turn waited 148.6 s, charged 212,938 rows (10.75 GiB), and then forwarded 449.
    • The price is the served prompt's: the router's notes and the replayed spans count as the prefill reads them.
    • A regenerate or an edit asks the slot's rows where its prefill will resume, the way the prefill asks them, and pays the rows from there. A prompt with images cannot ask the rows, so a regenerate or an edit with images takes no share and pays more.
    • A next turn whose copy leaves out the last answer's reasoning is charged from the end anchor. Before, the last answer was charged twice.
    • The floor a prefill's pages commit under holds the chunk the turn forwards, not a whole 4,096-row chunk. Where the forwarded rows are not known, it holds a whole chunk, as before.
    • Before the prefill's first forward the server compares the rows it forwards with the price (server/app.py _forward_backstop). When they need more workspace, the request's own reserve is raised, checked at the floor, and the log says [memory] <id> forwards <n> rows, priced at <m>: its workspace <a> -> <b> GiB, reserved. When the floor does not hold the raise, the lane gives way before the forward allocates anything: a streamed one, or one that asked for the long wait, waits and reads again; any other that runs alone ends with memory_full.

    A hand-back that frees nothing during a wait prints its line once, then a count once a minute, and the count again when the wait ends (--verbose only). Before, every one-second retry printed eight lines.

    Measured on one DGX Spark (2026-11-10, Flash-Next 3.05, 8 lanes, a synthetic chat of about 203,000 tokens through the chat endpoint, then short turns): every request line of the build had ws_rows equal to fwd. Follow-ups forwarded 931 to 1,059 rows, a regenerate 7,281 and an edit 2,737. No turn waited in that run, so a wait at the new price is not measured yet. Known gap (SRV-805, open): a cold read took more host memory than its reserve, 0.37 GiB more for a 3,412-row prompt and 0.44 GiB for a 203,415-row one. The cause is not known.

    How a round runs¶

    One thread runs every decoding lane's round (QSE_ROUND_RUNNER=1, SPD-201): the lanes' proposals, one packed draft, one joint verify pass, the walks and the tails (commits, penalties, stop strings, the stream). /health parallel.round_runner has its host and GPU milliseconds by phase. A lane of a family without a draft head joins the pass with its plain step as a one-row block (ENG-241). The 27B's joint pass runs from CUDA graphs once a pass shape has come QWEN38_JOINT_GRAPHS_AFTER times; a graphed pass gives each lane's logits, state and KV bit for bit what the eager pass gives (tools/joint_graph_check.py).

    NemotronH reads its routed experts once for the union a pass's rows pick, so its joint pass costs more with every row than a dense model's; at 8 lanes it keeps 16 rows (SPD-233). Where drafts do not pay, the runner takes the joint plain step: it learns at each lane count the tokens a GPU ms of its drafted rounds and of its plain rounds, decided on live rounds only (a round that captures a graph enters no rate), takes the better with a 3 % margin (QSE_RUNNER_LANE_MARGIN) and runs the other mode every 16th round (QSE_RUNNER_LANE_PROBE); a workload whose drafts pay keeps drafting. /health parallel.round_runner.lane_plain has the rates. nemotron-h.md has the family's numbers.

    Each graph owner captures on a stream of its own (SPD-223): engine/capture_lock.py lease_stream hands out a driver-created stream to one owner at a time (a lone draft graph, a packed draft set, the joint set, a slot's verify graphs) and takes it back only after the owner's graphs are reset. A graph's reset frees the cuBLAS workspace torch keeps for its capture stream, and every graph captured on that stream bakes the workspace into its GEMM nodes. With the streams of torch's shared pool, one owner's eviction freed the workspace of another owner's kept graph, and that graph's next replay wrote into freed memory: an illegal memory access at 4 and 8 greedy lanes. The same kernels are captured into the same pools, so every replay keeps its bits.

    Prompts that arrive together (SPD-245)¶

    Requests bound to lanes while no lane decodes form a burst (QSE_PREFILL_BURST, server/prefill_burst.py). Every member prefills before any of them decodes, so the lanes decode in joint rounds of all of them from the first round on instead of beside the prefills still waiting. With joint, the default, the members' prompts run in one layer-major forward (engine/model.py prefill_joint): each EXL3 projection is one call over every member's rows on a slab decoded once a layer, the row-wise kernels run once over all rows, and the mixers run one sequence at a time on its own engine. Every row is bit for bit what its own prefill gives (tests/gpu/test_prefill_joint_gpu.py); 8 prompts of 512 tokens took 3.55 s in one forward against 4.43 s one after another, in process. The joint forward takes a prompt of up to EXL3_CHUNK_UNTIL rows (512 on the 27B's EXL3 profiles) on a plain text forward; a longer prompt, an image or another weight format joins the burst with no job and prefills alone.

    Flash-Next runs its own joint prefill (QWEN38_FN_JOINT_PREFILL, engine/models/flashnext/joint_prefill.py, SPD-249), on in its profiles and off in the family's defaults. Each layer's experts run once over every member's rows; the rest of a layer runs a prompt at a time at its own rows, so every prompt ends bit for bit as its own prefill leaves it (tools/fn_joint_check.py --joint-prefill). It takes a prompt whose remaining rows fit one prefill chunk (QWEN38_FN_PREFILL_CHUNK) without images, and cuts the members into runs of at most one chunk of rows. A member's own steps before the forward (its open chain, its start, its KV pages) run on its own thread, so a failure there fails that member alone; a failure inside the forward fails every member of it. The trade: requests that arrive together get more tokens per second in total, and long prompts in a burst get their first token later, since every first token of the burst waits for the one forward.

    A member that would run the joint forward alone while another request is still on its way to a lane gives the turn back and waits for it, up to QSE_PREFILL_BURST_WAIT_S. A request with none on its way starts at once, so a lone request never waits. A request whose own question runs on this server (the router's class, package or library question before a chat turn, X-Tandem-Parent) is not on its way while the question runs, so the question never waits for the turn that waits for its answer (SRV-769). /health parallel.prefill_burst has the bursts, their members, the joint forwards and their rows, incoming, asking, held, held_own (holds for a member's own turn) and the last holds with the requests each waited for; the engine log has a [burst] line per hold.

    knob default what it does
    QSE_PREFILL_BURST joint joint: a burst's prompts in one forward; wait (or on): each prompt alone, the decodes after every member's prefill; off: no burst
    QSE_PREFILL_BURST_WAIT_S 10 how long a member waits for the others, then it goes on (counted as a timeout)
    QSE_PREFILL_BURST_ASKING out out: a request is not on its way while its own question runs; in: counted as on its way (before SRV-769)

    Only the order of the work moves, so a burst changes no token. It changes time to first token: a member's first token comes after every member's prefill.

    What a slot costs¶

    A side slot holds its own KV, recurrent state and verify graphs: about 104 KiB a token of window plus 7.5 GiB, most of it the pools of its 121 verify graphs. An 8,192-token slot took 6.9 to 7.5 GiB on the box; a 65,536-token slot is about 14 GiB (arithmetic). On a 128 GB DGX Spark next to the engine's own caches, --parallel 2 with the default window fits; four slots need shorter windows (the measurements below used 8,192).

    Beside the small models¶

    A box that also runs the decision models (Laya) and the narrator has less room for side slots. The plan for a 128 GB DGX Spark serving the 27B at its 262,144-token window, Laya-english, the narrator (Qwen3.5-2B) and the shadow reader (measured on 0.3.42-test, 2026-10-06):

    GiB
    unified memory 121.6
    the engine between requests (caches full, the 70 GiB ceiling) and its 77 GiB peak +8.6 at the peak
    Laya-english inside the engine 1.6
    the narrator (Qwen3.5-2B) 4.2
    the shadow reader (Qwen3.5-0.8B) and its session states (cap 4) 1.5 + up to 4
    MemAvailable at the worst moment with one sequence about 22.7

    Four slots of 8,192 tokens (about 25 GiB with their graphs) do not fit beside that. Two do, with one side slot of 65,536 tokens and --side-graphs off (about 8 GiB). The window matters more than the number of slots: a request takes a side slot only when its prompt, its max_tokens and the conductor's margin (64 tokens, 8,192 more when the conductor shapes the request) fit. Over seven days on that box, opencode's prompts were 103k tokens at the median with max_tokens 65,536 (they always need slot 0); Open WebUI's were 19k with max_tokens 32,768, and a 65,536-token side window takes 57 % of them, an 8,192-token one none.

    Side slots are built while the engine loads, before ops/start.sh asks the residency planner for Laya and the narrator. The planner then sees what the side slot took, so the residency document's claims must be the models' measured sizes (the reference box: decider 3.0, narrator 4.5 GiB, margin 5); with the old declared ones (8.2 and 6.0, margin 6) both are refused. Since 0.11.3 the shipped decider claim is the measured 3.0 GiB, and the narrator is off by default (SRV-534). A model the planner refuses is journaled in residency.jsonl and the engine serves without it.

    On that box one decider of three and the shadow reader stay unloaded, and that is the planner doing its job (0.4.1). The numbers from residency.jsonl on 0.3.51-test: MemAvailable 28.97 GiB, the engine at 76.4 GiB of a declared peak of 84.65 (77 plus the side slot's 7.65), so 8.25 GiB of growth is still to come; the shadow reader claims 6.5 GiB and would leave 14.22 GiB, under the 15 GiB floor itself; a second decider (3.0 GiB) would leave 17.72, above the floor and under floor plus the 4 GiB margin. The growth is not counted twice. The parallel admission checks MemAvailable only while two requests are in flight; a request alone is admitted by the engine's own peak (server/slots.py Admission.reserve), so a single 262k prefill can take those 8.25 GiB whatever else has loaded, and the planner's growth is the one thing that keeps the floor then. The Deciders screen says so in words: "not loaded: kept free for requests", with the numbers, and names the shadow reader when the last refusal was its. Room for them comes from a lower declared peak or a smaller margin, both edits in the residency document that trade cache room or safety for a model, not from the planner.

    While two requests run, Laya answers only when slot 0 is idle: a decision forward takes the engine lock (stage A). A request that takes a side slot arrives while slot 0 is busy, so its router question passes Laya's 400 ms and goes to the next stage, as it does for any request that arrives while the engine is busy with one sequence. The narrator serves both requests; a second request asking at the same moment gets the template line for that step.

    The memory policy and the side slots¶

    The side slots' buffers are the engine's for good, so the engine's memory policy (engine/cache.py Budget) raises its ceiling and peak by what they took when they are built (7.65 GiB for one 65,536-token slot without graphs). From 0.3.44-test to 0.3.46-test the first request's residency document set the two limits again to their configured figures (70 and 77 GiB) and the raise was gone: the caches had no room left (live on 0.3.46-test: 131 anchors, 2 guest stashes, a park and a pin refused in one evening), and a guest whose stash was refused cut the resident rows at its start, so the next turn of a 41,474-token Open WebUI conversation read 41,749 tokens again (56 s). Since 0.3.47-test the slots' bytes are kept apart (Budget.fixed, in /health cache.memory.fixed) and added to every value the limits get. Replayed on the live engine with one build (n = 1 each): a 32,875-token conversation and two new user messages read 0 % from the cache at a 70 GiB ceiling (67.5 s and 70.7 s) and 99.9 % and 99.3 % at 78 GiB (6.4 s and 9.4 s).

    The shared KV pool¶

    QSE_KV_POOL=on (--kv-pool on, SRV-307, 2026-10-10). Without it every slot allocates its whole window at load: 104.25 KiB a token, 106,752 bytes (64 KiB of engine attention KV for the 16 full-attention layers, 2 × 20 KiB of the two drafter arms' context KV, 256 B of rotary table). Four slots of 262,144 tokens would be ~104 GiB before the first request; the box could afford one long window and three short ones.

    With the pool, engine/kvpool.py reserves each KV tensor's full size as virtual addresses (cuMemAddressReserve) and maps 2 MiB physical pages (cuMemCreate/cuMemMap, the allocation granularity on GB10) only for the rows a conversation writes. The tensor has the static buffer's shape, dtype and strides, so every kernel, every view and every captured CUDA graph is unchanged, and the results are bit-identical by construction (tests/gpu/test_kvpool_identity_gpu.py: logits, KV rows, the recurrent state and a greedy spec-tree decode equal at 8k, 32k and 128k).

    • Commit. Every engine forward commits start + rows plus a margin (QSE_KV_MARGIN_ROWS, 256) before it runs; a generation commits its prompt first; every copy into the KV (a store restore, the pin, the park, the guest stash, the disk tier, the NVMe spill, a side slot's carry) commits its rows before it writes them. A fresh page is zeroed, as torch.zeros was.
    • Give back. When a request ends, its slot keeps the rows its conversation still holds (the KV length, the resident prefix's valid rows, a side slot's carried end) and the pages past them go back.
    • Under pressure a commit that would take MemAvailable under QSE_KV_HARD_FLOOR_GB (10) first asks the memory policy's levels (store, anchors, end, stash, park, pin) and the allocator's free blocks, then the small models (0.6.1, server/rolemem.py: the shadow reader, then the narrator; see below), then the conversations idle side slots keep (oldest first), then slot 0's idle conversation (to the NVMe first when the spill is on); only if none of that is enough is the commit refused. A request that does not fit the admission takes the same levels back, the caches left out, before it waits.
    • The small models under pressure (0.6.1). An unloaded role gets a memory hold: its callers get unloaded_for_memory at once (no narrator lines, the template line instead; the shadow reader's journal-only answers stop) and nothing loads it on demand. It loads again through the residency planner, one role at a time and the narrator before the shadow reader, once the headroom (MemAvailable less the caches' growth and the requests' reservations) has stayed at QSE_PARALLEL_FLOOR_GB + its claim + QSE_ROLE_RELOAD_MARGIN_GB (4) for QSE_ROLE_RELOAD_S (60 s) with no request waiting and no reclaim in that time. A role unloaded again within QSE_ROLE_THRASH_S (600 s) of its reload waits twice as long next time (up to QSE_ROLE_MAX_HOLD_S). The Laya deciders stay loaded unless QSE_ROLE_UNLOAD_LAYA=on: they answer the router's questions, and their fallback, Qwen's own answer, can choose another class, another package or another effort, which changes what the model is given, and costs an engine turn and guest KV rows exactly while memory is short. /health roles and the System view's memory panel show each role as loaded, unloaded_for_memory or reloading; every unload and reload is a [roles] log line and a row of the residency journal. While no Laya model is loaded because the planner refused it, /health roles.laya.refused names the model, the reason and the planner's numbers, and the log has one [deciders] WARNING line (0.11.3, SRV-534): on a model whose fit leaves the class question to Laya, no class is decided then. Qwen's output does not depend on the roles (their own memory pools and stream): tests/gpu/test_roles_dynamic_gpu.py checks tokens, blocks and prefill logits loaded, out and reloaded.
    • Admission reserves, beside a request's prefill workspace, the KV pages its prompt and max_tokens may still commit on its slot, credited as its slot commits them. A request that does not fit waits (SRV-305): its stream carries "waiting: memory is almost full" and the rest of that line every 15 s (Open WebUI's status line, opencode's reasoning; the states lines are stripped from a turn sent back), the header X-Tandem-Wait: memory, the Parallel view shows the lane as waiting_memory and counts totals.waiting_memory; a streamed request waits up to QSE_MEM_WAIT_S (SRV-787; until then --request-timeout), a non-streamed one gets a 503 memory_wait_timeout with Retry-After after --queue-timeout.
    • The memory policy no longer holds slot 0's window: its ceiling and peak drop by it (26 GiB at 262,144), so the residency planner sees the uncommitted window as free and loads the narrator and the Laya decider beside four slots. /health kv_pool shows the committed pages by slot and by kind (committed_by_kind_gib: engine KV, drafter KV). The System view's memory split counts the KV as these committed pages, outside the allocator, never as a paged tensor's size (that is its reserved address range, kv_reserved_va, 26.6 GiB a 262,144-row slot and no memory), and adds outside (the CUDA context, the host side, other programs) so that the bar sums to MemTotal - MemAvailable.

    One memory policy for every prefill (0.15.1, 2026-11-02, SRV-773, SRV-775). Before a request reserves its bytes, the engine's memory gate runs on its slot, slot 0 and every side slot alike, on the reserve as it is, and charges the workspace of the rows the prefill forwards from where the prompt resumes in place (the end anchor, the last prompt's end, the anchors). On Flash-Next a resumed turn of 21 rows took 0.10 GiB at every context from 8k to 146k tokens; the old charge, the whole context's (2.75 to 10.39 GiB), refused such a turn on slot 0 while the side slots ran with no gate at all. A side slot's gate runs the peak stage only; the ceiling stage, which walks the allocator's pools, stays slot 0's. A side slot's gate whose reserve plus workspace stays 0.5 GiB under the peak admits on one reading without the policy's lock, which slot 0's gate holds (cache.memory.fast_gates; never under QSE_PEAK_STRICT). The admission then counts every prefill's workspace by its rows while it runs (on Flash-Next a cold prompt without the gate's 2.75 GiB floor) and gives it back when the prefill has run (parallel.admission.ws_in_flight_gib). It caps the caches' growth and the workspaces of the prefills in flight at the engine's room to its peak, as before: the gate keeps each prefill it admits under the peak. A lone admit over the peak counts its workspace against the box floor, in full less the allocator's free default-pool blocks it takes before any new memory (Budget.workspace_spare; MemAvailable already leaves the engine's whole reserve out, those blocks too). A request alone is checked against the floor too (alone, lone_checked).

    A prefill the gate still refuses after shedding waits in the memory line while another prefill runs (peak_waits; its line names the peak), and runs alone over the peak when none does, counted in /health memory.over_peak_admits, with over_peak_slot and the reserve over the peak now in over_peak_gib: a long-lived server's reserve holds graph scratch no shed lowers, so a lone request would wait for good. QSE_PEAK_STRICT=1 makes a lone request wait too. A prefill no reserve could ever take (the engine's load plus its workspace over the peak) gets its 503 at once, and no idle conversation is reclaimed for a request the gate refuses while another prefill runs. The rows a prefill forwards are priced again before every gate pass and before its reservation, and a continuation keeps its end anchor through the gate's passes (2026-11-02). A request that waits for memory leaves the prefill burst, so the others prefill without it, and one that waits for a prefill in flight runs the gate again only when a prefill has run, its resume point moved or 5 s passed.

    Which request goes where¶

    Slot 0 is the engine as it always was: the full window, the resident conversation, the disk tier and the side lane. A request takes a side slot only when slot 0 is busy, its prompt plus max_tokens fits the side window, and it does not continue slot 0's resident conversation (that turn waits for slot 0 up to QWEN38_SIDE_SLOT0_WAIT_S, 3 s, and resumes in place; after that it takes a free side slot, below). One kind of request takes an idle side slot even when slot 0 is free (0.3.47-test, SRV-207): a guest of slot 0's conversation, that is, a short request (at most --resident-guest-max tokens and under a quarter of the conversation) that shares less than one prefill chunk with it, while slot 0 holds at least two chunks. The router's own questions before a new user message (the class, the package: 150 to 450 tokens) and a client's title, tags and follow-up tasks are such requests. On slot 0 a guest writes over the rows the conversation's next turn resumes from and only the guest stash puts them back; on a side slot it costs the same prefill and touches nothing of slot 0. A guest short enough for the side lane takes the idle side slot too; a side-lane request that is no guest is still served at slot 0's safe points, except TandemLLM's own questions (SPD-249, QWEN38_OWN_SIDE=on): with slot 0 busy, the router's question takes an idle side slot whose last end no conversation waits for, and a question too long for the lane does not wait SIDE_AFTER_OWN_S (15 s) behind another one of TandemLLM's own jobs on slot 0. Its rows are nobody's to carry (no_carry). With every side slot busy it runs on slot 0 with the stash, as before (QWEN38_SIDE_GUESTS=off restores that for every guest). Everything else about the request is served by the same code: the conductor, the monitor, tool calls, structured outputs, streaming.

    A request with images takes a side slot the way a text request does (SRV-629). On 2026-10-19 two Chat-tab agent runs called render_page, and every later request carried 3 to 8 screenshots. The router sent each of them to slot 0, so all 31 requests of both chats ran there: 56.6 min of wall time for 18.9 min of decoding, with slot 1 idle. Nothing in the engine needed slot 0. Each side slot is its own engine over the same weights, with its own image context and rotary offset, and the vision tower runs inside the slot's prefill. Now the router expands each image to its rows on the host and gives them the image's key, as the caches do (_mm_keys). Window, output cut and memory admission count those rows: a screenshot of 1,280 by 800 pixels is 1,000 rows, not one placeholder. Every continuation test reads the same keys. A turn with the same screenshots resumes on the slot that holds its rows, and another screenshot in the same place starts a new conversation. An end kept after images and carried into slot 0 keeps its rotary offset. A request with images is never a guest of slot 0. The [parallel] line says images=N rows=R. QWEN38_SIDE_IMAGES=off sends images to slot 0 only, as 0.12.0 did. Super VL's RADIO tower builds its own context and stays on slot 0.

    "Continues slot 0's conversation" is judged on the client's tokens (0.3.46-test, SRV-197): at the end of every request on slot 0 whose rows stay resident, the server keeps that prompt as the client's messages render it (no router note, no replayed span, no generated row). A new request whose rendered prompt starts with all of it, within one prefill chunk, and which is at least a chunk long, waits for slot 0, also when slot 0 is held only for a moment by TandemLLM's own work (the shadow reader, a summary being prepared), which gives way to it. Until 0.3.45-test the test compared the request with the resident rows themselves; under a conductor plan those rows also hold the router's notes and the end of the last generation, so no agent turn ever counted as a continuation, and a turn that met slot 0 held by the shadow reader took the side slot and read its whole conversation again (an opencode session's cached share fell from about 0.97 to 0.4-0.68). QWEN38_SIDE_CONTINUE=resident restores the old test, for an A/B. And TandemLLM's own work never sends a client's request to a side slot: while slot 0 is held only by it (the shadow reader, a summary being prepared, the memory writer, the router's question), a request keeps waiting for slot 0, which that work gives up at its next safe point, for up to 15 s; a side slot is for a second client's request. Two long agent sessions at once mostly take turns on slot 0, each resuming its own conversation (the resident one in place, the other from the park or the disk): a side slot keeps no conversation, so a long agent turn there reads its whole prompt again, and the GPU it shares slows slot 0 too. Measured with two opencode sessions started together (n = 1 each, needs verification): taking turns on slot 0, both done in 301 s with cached shares 0.90 and 1.00; with one session sent to the side slot whenever slot 0 was busy, 490 s, that session at 0.26 (17 of 18 turns on the side slot, 379 s of prefill); one after the other, 193 s. A side slot pays off for requests slot 0 holds nothing for: a new conversation, a short chat, a script. The [parallel] log line names the slot, the numbers it was chosen on and who held slot 0; the [req] line and the usage ledger (schema 7, slot) record the slot of every request.

    Sharing a client's head is not continuing a conversation (0.3.49-test, SRV-223). Open WebUI's system prompt and tool block render to about 6,700 tokens before the first user message, opencode's to about 7,400, the same for every chat of that client. The next turn of the same chat shares its first message and everything after it and still waits for slot 0. QWEN38_SIDE_CONV=off is the old rule.

    A conversation that ran on a side slot is carried into slot 0 (0.4.1, SRV-213). A new chat or agent session that starts beside a long conversation on slot 0 is a guest of it by size and runs on the idle side slot; once it outgrows the guest limit its next turn runs on slot 0, and until 0.4.1 it read everything past its client's head on the NVMe again there: 8.7k tokens in 18.3 s in UX2's O07, cached 0.44 and 17.0 s to the first token in UX1's W11 beside an 80,000-token conversation. At the end of every request on a side slot the server notes what the slot's rows hold. The conversation's next turn on slot 0 moves slot 0's conversation out the way a request of another session does (to the NVMe when it is longer than the park holds, else to the park), copies the side slot's rows and its state at the end into slot 0, about 104 KiB a token, and resumes at that end as at any end anchor, the hidden spans and Open WebUI's reasoning-less copy included. The ledger's cache_source is side. A short request unrelated to slot 0's conversation (the router's question before the next user message, a title task) leaves such a side slot alone for 10 minutes while slot 0 is free, and runs on slot 0 with the stash. QWEN38_SIDE_CARRY=off is 0.4.0's re-read. tests/test_side_carry.py checks that the carried turn writes the same greedy tokens as the conversation run on slot 0 throughout.

    A side slot keeps its conversation (0.4.8-test, FX16). On 2026-10-08 two Open WebUI chats ran at once: a 64,000-token tool loop on slot 0 and a new chat on the side slot, decoding beside it. The new chat's next turn found slot 0 idle and was carried into it, which moved the long chat to the NVMe (83,160 tokens, 4.1 s); from then on neither chat could take the side slot, because the window was compared with the prompt plus the whole served max_tokens of 32,768 (any prompt past about 24,000 tokens was "too long"), and the two took turns on slot 0 with waits of 31 to 180 s while the side slot stood idle. Three changes. A side slot takes a request whose window leaves it at least QWEN38_SIDE_MIN_ROOM rows of output (16,384, the high thinking budget), with max_tokens cut to the room; the [parallel] line says max_tokens N -> M (the slot's window).     A guest chat keeps its end (SPD-257).     A turn that continues slot 0's conversation never waits minutes behind another conversation's run (0.8.2).     A conversation stays on the slot that holds its rows (0.11.3, SRV-528).     The text¶

    Beside other requests, a request writes what it writes alone up to a near tie. A joint round verifies the request's tree cut to its share, a different tree shape than alone, and the shape of the verified tree can move a token whose two best candidates score almost the same (exactness.md). On 30 prompts (prose, code, chat, 256 tokens), 17 of 30 were identical to their alone text at two requests and 15 of 30 at four, every first difference at a top-2 gap of 0.0019 to 0.118 nats. Two runs of one request alone can also part at a near tie, for the same reason (exactness.md). The rows of a joint projection are the bits they are alone (tools/parallel_verify_check.py).

    On Flash-Next¶

    The same flags work on Flash-Next since ENG-241, and its profiles turn them on (QSE_PARALLEL=3, QSE_KV_POOL=on in ops/profiles/_flashnext.env, 1d4af64d). On 3.05, on fresh servers, greedy: three requests arriving together took 27.18 s against 27.03 s one after the other, the same total throughput. The first tokens came at 2.2 to 6.1 s instead of up to about 20 s for the last of three, and every answer equalled its single-stream answer. One request alone decoded at 45.78 tok/s with three slots and the pool, against 45.79 with one slot, with the same text. At the profile's default window (262,144) with two 65,536-token side slots, a 260,800-token prompt kept MemAvailable at 31.6 GiB or more (the floor is 15). So the slots buy time to first token for the second and third request, not throughput.

    Seeing it¶

    /health and the dashboard's System page carry parallel (the slots, the GPU turn, the rounds by size, the admission) only when side slots exist. The Parallel view shows each engine lane's slot. tools/parallel_bench.py measures c1, c2 and c4 totals, each request against its alone text, and proves from /health that the requests decoded together; a level whose windows never show c slots decoding at once is reported as invalid.

    Not yet¶

    Side slots do not resume slot 0's resident prefix, and have none of slot 0's caches in memory (they read its disk tier, nothing else). A conversation's turns that stay on a side slot read their prompt again each turn from the disk tier's head; only the move to slot 0 carries the rows (SRV-201 is the side slot keeping its own conversation). Two requests reach about 1.4x, not 2x: a joint pass of 32 rows costs more than one of 16 at today's kernels.
