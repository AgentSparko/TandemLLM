# Fleet API contract v1

These files are the truth for `/v1/fleet/*`, the API of TandemApp's controller: the Sparks it manages, the links between them, the deployments, per-node metrics, memory, events, alerts, rules, the node actions, the saved window layouts, discovery, the Add Spark wizard's session and App settings (SRV-723, SRV-725, SRV-727, SRV-729, SRV-731, VIS-246, VIS-250, VIS-256). The dashboard's mock fleet (`dashboard/mock/fleet.ts`) validates every answer against them (`npm run test:contract` in `dashboard/`); the controller's tests will hold its real responses to the same files. They live beside `dashboard-v1` so the two contracts can change on their own.

The schemas use the same JSON Schema 2020-12 subset as `dashboard-v1`; each file is self-contained. `additionalProperties` is `false` everywhere except a window's `ref`, which holds the window kind's own keys (a node, a file, a metric).

## Rules the schemas cannot express

- Times are Unix seconds. A metric answer's sample `i` is at `t0 + i * step_s`; the last sample is at or before the request. `step_s` is the range's span over its sample count less one (5m: 151 samples, 1h: 121, 6h: 145, 24h: 145, 7d: 169, 30d: 721); the end sits on a 30 s grid, or on the step when the step is finer. The scope bar offers 5m to 7d; 30d (hourly) is for a month of energy on Usage.
- The controller sends every metric per node and never aggregates: the page computes Total, Stacked, Lines, Split and Table from `series` with `agg`. `sum` metrics add up (tok/s, requests, power, memory, disk, network), `mean` and `max` do not, `maxmean` (temperatures) shows the max with the mean dashed. A `null` value is no sample (the node was off or not yet paired, or has no fabric port): aggregates skip it, they never count it as zero.
- `source=all` gives one series per paired node, `node:<id>` one, `deployment:<id>` one per member; with a deployment, `tps` and `req` count that deployment's tokens and requests only, the hardware metrics the whole member. A Split's tokens count once per stage at half, so the members add up to the deployment's total. `cap` is the per-node capacity of the metric (`mem`: the usable unified memory), else `null`.
- A node's `colour` is its identity, 1 to 8: 1 to 4 are the four node hues, 5 to 8 the same hues drawn hollow and dashed. Node ids are stable (certificate fingerprint and DMI serial); an address or tunnel port may change, the id does not.
- A `PATCH` of a node is refused (400) for an alias another node has (letter case aside) or a colour another node has: the alias and the colour name one node each. A new node gets the first colour no node has.
- A node's `status` is never only a colour in the UI: `up` ●, `draining` ◐, `off` ○, `alert` ⚠, each with `status_text`.
- An event's and an alert's `node` is a node id, `all` (the whole fleet) or `host` (the controller's machine). Event types: `node` (up, off, draining, paired, released, taken over, a new address), `engine` (an engine backend down, up, started, restarted, stopped), `deploy` (a deployment's status), `alert` (fired with the alert's severity, `resolved`, or acknowledged with severity null), `controller` (the controller's start and stop, node `host`), and `failover`, `link`, `weights`, `update`.
- An alert's `id` names its rule and subject (`gpu-temp:<node>`); one that resolves and fires again is a new alert with the same id, unacknowledged. `action.route` is a dashboard route (`#/hardware?scope=node:<id>`, `#/sparks/<id>`, `#/models`, `#/app`). `rule` is the rule's name and condition.
- A rule's `threshold` is null for a rule without one (a node that does not answer); `unit` goes with it. A rule fires once its condition holds for `for_s` and resolves once the value is back past the threshold by the rule's own margin for its own time (hysteresis). `PATCH` refuses a `threshold` for a rule without one, a `scope` other than `all` or `node:<id>` of a node in the fleet (a `host` rule's scope stays), and a `notify` other than `app` and `system`. `app` is the alerts list; `system` is the page's to show as a system notification; the controller makes no outbound call. Edits need what the other writes need.
- A layout is one page on one device class (VIS-256). A `PUT` stores the body with `saved_at` set to the controller's clock, whatever the body said: the last write wins. A window's `at` is its dock (`right`, `bottom`), `float` or `min`; `prev` is where a minimised one returns to; `x`, `y`, `w`, `h` place it while it floats (pixels in the page's work area) and `z` orders the floating ones. A dock's `f` is its share of the work area, `act` the window its tabs show. `saved_at` is null for the default a page answers before its first save; the page then lays out its own default windows.
- A node's `pairing` (SEC-4): `local` is the controller's own machine, `paired` a node whose certificate the controller pins (`via` `code` or `ssh`, `fingerprint` the pinned certificate's SHA-256, `host_key` the SSH host key an SSH pairing confirmed), `unpaired` a node record without trust yet (`off`, "not paired"). Pairing, release and take-over need the admin password (a session from `/v1/fleet/session` or the bearer token), or a caller on the controller's own machine; with no password set, only the latter.
- Pairing errors: 403 `wrong_code` (also when a certificate was swapped on the way: the two look alike on purpose), 410 `code_spent` (expired, used, or five wrong codes), 409 `owned` (another TandemApp owns the node: take it over on the node, or `takeover: true` over SSH), 409 `conflict`, 409 `host_key_changed`, 409 `not_installed`, 502 `unreachable` and `ssh_failed`, 429 `too_many` (ten attempts a minute).
- A sample's blocks and fields are present only when the board exposes them: a GB10 has no fan reading, no power cap and no GPU memory of its own, a box without a ConnectX port no `net.fabric`. The page says "not exposed by this board" for an absent field, never 0. `via` `process` is this machine read without its agent: the fleet's keys, the GPUs and memory only; `none` is a node without a source (off, not paired), with `note` saying why. `age_s` is how old the sample is when the controller answers.
- A node's `drain` (VIS-250, concept B5): a drained node takes no new request through the controller's gateway: a route's backend on it is skipped for the route's fallbacks, and with none the client gets 503 `node_draining` with `Retry-After: 30`. Requests in flight finish; `inflight` is the larger of the gateway's own on the node's engines and the engines' own count. While a drain is set the node's `status` is `draining` (◐), `drain.state` `draining` while something is in flight and `drained` after; an `off` node stays `off`. The drain is kept until `undrain`, across a restart of the controller.
- Node actions: a plan (`GET .../actions/{action}`) answers for every action, `allowed` false with `blocked` in words when it may not run (`restart-engine` on an engine TandemNode did not start: "not managed by TandemNode"; `reboot` and `update` on a node whose owner did not set them up; anything but drain on a node read without its agent; `forget` of the controller's own node; `release-lease` of an owned node). `destructive` actions (all but drain and undrain) carry `confirm`, single use, for five minutes: their POST without it is 428 `confirm_required`, with a spent, stale or another action's 409 `confirm_invalid`; a plan that does not allow its action answers its POST 409 (`not_managed`, `no_agent`, `not_rented`, `conflict`), `release-lease` of a rented node 501 `not_built` until rental support. `reboot` and `update` of a virtual node (a second agent on one machine) are simulated: its plan says so and its job's `simulated` is true. `forget` is the release of `DELETE /v1/fleet/nodes/{id}`; it and `release-lease` need what pairing needs, the other actions what the other writes need. A plan is a read.
- A link's `test` is its last link test: `gbps` null when the bandwidth part failed (`note` says why), `rtt_ms` the median round trip. The controller tests a LAN link to a node's agent; 409 `no_wire` for the node it runs on, `no_agent` for a link without an agent at its far end, `unreachable` for a node that does not answer.
- Discovery (SRV-727, `proxy/discovery.py`, `proxy/mdns.py`). Sources: mDNS (`_tandemnode._tcp`, whose TXT says the node id, `class`, TandemLLM's version, the box by its DMI, whether it is paired and to whom, the pairing window's port while one is open and the SSH host key; `_ssh._tcp` and `_workstation._tcp` for names), the LAN scan, `~/.ssh/config` (its Host entries resolved as ssh does, never connected to), add by address, and what pairing learned (the DMI an SSH-once login read, a node owned elsewhere). A run (`POST`) browses mDNS for 3 s, reads `~/.ssh/config` and asks the scan's question; rows arrive while it runs: poll `GET ?since=<cursor>` (about once a second) for the rows changed after the cursor; `full` is true when `rows` is the whole list (no `since`, or one from an earlier run), and `gone` names the rows that left (merged into another). Every discovery route, `GET` included, needs what the other writes need: the list carries `~/.ssh/config`'s hosts and what answers on the LAN.
- The LAN scan asks first. No packet goes to any address's port 22 before a write answers `scan.question` ("Scan 192.0.2.0/24 for SSH?") with `POST /v1/fleet/discovery/scan {subnet}` naming that subnet; another subnet is 400, a scan running 409 `busy`, no LAN 409 `conflict`, the permission off 409 `lan_denied`. The subnet is the interface's when it is a /24 or smaller, else the /24 around its address. Each address of it gets one TCP connect to port 22 (`timeout_ms`, 300) and the banner the server sends first, nothing else (never a byte sent, never a login), at most `rate_per_s` connects a second; `total`, `done` and `open` count its progress, `by` says who said yes (and the audit). A new run asks again. Add by address reads one address's banner the same way and connects to the agent's ports (7700, 7701).
- One row per box: sightings that share the node id, the SSH host key (the TXT's, or the user's and the controller's known_hosts, hashed entries too), an address or an mDNS name are one row; two different node ids never are (a virtual node shares its machine's address). A row's `id` follows its strongest key (node id, host key, address), so it can change when a later sighting joins it: the old id is then in `gone`.
- A row's `kind`: `spark` (TandemNode answered: `title` "Spark with TandemLLM x.y", `detail` the box, the version and "not paired", "pairing code showing on the node", "paired with this TandemApp" or "in this fleet"), `gb10` (a GB10 box by its DMI, read in an SSH-once login that found TandemNode not installed: "GB10 box, nothing installed"), `host` (not a Spark: by its DMI, or its SSH banner names an OS other than DGX OS's Ubuntu 24.04 or later: "Linux host, not a Spark", "Windows host, not a Spark" or "Host, not a Spark"), `owned` (a Spark another TandemApp owns, by its TXT or a pairing refused 409: "Spark owned by another TandemApp") or `unknown` ("Unknown device": an Ubuntu 24.04 banner, a `~/.ssh/config` entry or an mDNS name says too little; a login tells). The GB10 vendors (NVIDIA DGX Spark, ASUS Ascent GX10, Dell Pro Max with GB10, Lenovo ThinkStation PGX, MSI EdgeXpert, Gigabyte AI TOP ATOM, Acer Veriton GN100, HP ZGX Nano G1n) are one table in `proxy/discovery.py` with the source of each match; any box whose DMI product family is "DGX Spark" counts too. `connect` lists what the wizard's Connect step can do: `code`, `ssh`, `takeover`; empty for a node in the fleet or a host that is not a Spark. `fleet` is the fleet's node id when the box is in the fleet.
- `local_network` is macOS's Local Network permission for the controller: `not_needed` on any other system, `not_asked` before the first run, `granted` once a browse's packets left, `denied` when macOS refused them (`text` says so with `settings`, where to turn it on). While it is `denied` the scan is refused; `~/.ssh/config`, add by address, the ssh line and pairing by address keep working (a LAN address may still be blocked for the controller: its error then says so).
- `POST /v1/fleet/discovery/target {line}` reads a pasted ssh command (a rented or remote node: no discovery): `-p`, `-l`, `-i`, `-J` (comma-separated jump hosts, `[user@]host[:port]`), `-o Port/User/IdentityFile/ProxyJump` and `ssh://user@host:port`, the first value of each winning as in ssh. An option that runs a command (`ProxyCommand`, `LocalCommand`, `KnownHostsCommand` and the like) is refused 400; forwards, other options and a remote command are dropped with a `warning`. `route` is the hops in order, the node last; `remote` is true for a global address, a DNS name or a route through a jump host.
- The Add Spark wizard (VIS-246, `proxy/addspark.py`). One session is active at a time; `POST /v1/fleet/add` while one is open is 409 `busy` unless `replace`. A session's `step` is where the user is (find, connect, check, install, link, name, done); the page gates Next, the controller refuses what may not happen. Connect pairs as `/pair` and `/pair/ssh` do (their errors); an SSH login that finds nothing installed answers the session with the target `bare` (a 200), and discovery's row turns `gb10`. Check runs `proxy/preflight.py`'s script through the node's agent when it is paired (`GET /node/preflight`), else over SSH once; each row is `ok`, `warn` or `fail` with its value and, for anything but `ok`, its `fix`. A paired node at the fleet's version gets `install.state` `skip`; another version is a `fail` row and Install answers 409 `version_mismatch` (also when this controller's own version is not the fleet's); a red row is 409 `preflight_failed`. Install (`proxy/nodeinstall.py`) runs per bare target: `check`, `upload` (the wheel this controller builds of its own copy, sha256 checked), `agent` (a venv and pip), `engine` (install.sh `--runtime-only` at the fleet's tag: the engine's source and Python, never weights), `unit` (the systemd user unit, started) and `pair` (SSH once's adopt); the session carries each step's state and the last 400 log lines; a controller that stops mid-install marks it `failed` (`interrupted`) at its next start. Link: with fewer than two new nodes on the LAN its state is `not_needed` with `why`; `test` runs each new node's LAN link test, `configure` is 501 `not_built` until the rented pair (step 7). `step: done` applies the Name step's drafts as `PATCH /v1/fleet/nodes/{id}` does (its 400s) and ends the session. Errors: 409 `busy`, `conflict`, `host_key_unconfirmed`, `secret_needed`, `version_mismatch`, `preflight_failed`; 501 `not_built`.
- Secrets in the wizard. A password or a pasted key is in no session, database row, log line or answer: `secret.held` says whether this controller's memory holds one for the target (30 minutes at most, until the install takes it, the session ends or the controller stops); `secret_needed` asks for it again. A key file is a path on the controller's machine, read by ssh there. A rented node's pasted key is kept as a 0600 file beside the controller's certificate while the node is in the fleet (its tunnel logs in with it) and removed with the node. Keychain: a browser app has no access to the macOS Keychain; until the native shell, TandemApp keeps no secret of the user's at all, and its own certificate and keys are files with mode 0600.
- Rented and remote nodes. A target from an ssh line with `rented: {lease_end, cost_per_hour?}` (or any remote one: a global address, a DNS name, a jump host) is paired with `tunnel`: its agent stays on its own loopback and the controller reaches it through `ssh -L` (`proxy/sshtunnel.py`) with the key it was given; its record's `transport` is `tunnel`, its `lease_end` and `cost_per_hour` set, its tags `rented`. The rule `lease` (`Lease ends`, `lease_left` < 24 h, warn, app and system) fires once per lease and resolves when it is extended or the node leaves; a session's `reminders` say when it will fire.
- Metric keys: `tps` decode tok/s (sum), `req` active requests (sum), `ttft` TTFT p50 ms of the requests that ended in the sample's window (mean across nodes), `gpu` GPU % (mean), `power` W (sum), `temp` GPU °C (maxmean), `sm` and `memclk` MHz (mean), `mem` unified memory used GiB (sum), `cpu` % (mean), `disk` MB/s (sum), `lan` MB/s (sum), `fabric` Gb/s (sum), `rtt` ms from the controller (max).

- The fleet update (OPS-234, `proxy/fleetupdate.py`). A node needs the update when the TandemNode it runs reports a version other than `target` (the whole version: a local label counts). The plan's steps: `idle` (serves nothing, no drain), `replica` (another member of each of its deployments serves: drained, updated, rejoined, alone), `single` (a deployment only it serves: `downtime` says what is not served), `split` (a Split's members together). A Split with a member that cannot be updated is in `refused` and none of its members is updated; `?nodes=` (and the POST's `nodes`) that take one member of a Split and not another make the plan `blocked`, its POST 409 `partial_split`. The POST needs the plan's `confirm` (428, 409 `confirm_invalid`); a second while one runs is 409. `stop` ends the job before its next step (`state` `stopped`). A controller restarted during a job resumes it. Replicas and Splits are the deployment records (SRV-731); a node is drained before its update (no new request, no new conversation, what is in flight finishes within 600 s) and rejoins once its engines answer and each deployment it serves gives one token (300 s).
- The rule `version-mismatch` (`One release on every node`, metric `versions`, warn, app) fires one alert `version-mismatch:all` with node `all` once the answering nodes run more than one release for 60 s, its action `#/sparks?update=1`; it holds while an update runs.
- The controller's host (OPS-234, `proxy/ctlmove.py`). A move to a Spark (push) and a take (pull) are jobs: GET `/v1/fleet/controller` shows the last one. A move's plan refuses a rented node, one reached through a tunnel, one not paired or not answering, a controller that moved already, a second move; its POST needs the plan's confirm and, when this controller has no admin password, `password` (32 or more characters, no spaces, as `TANDEM_ADMIN_TOKEN` must be; 409 `password_needed`). A node's `how`: `repin` (its owner pin handed to the new controller), `release` (the new controller's own machine, read over its loopback), `own` (this controller's own machine, its agent handed on with its LAN address), `stays` (with `why`). Once a move is done, `moved_to` says where, the nodes are gone from this controller and the page follows. A take is refused 409 `not_empty` by a controller with a fleet of its own. Moves, handovers, takes and the update need what pairing needs.
- The deployments (SRV-731, `proxy/deployments.py`). A deployment is a record (`record` true; `deployments` in the config database) or a Single derived from a model an engine on a node serves that no record covers (`record` false, its id the model's id at the gateway, `<backend>/<id>` when another has it): so a node's engine that nobody manages (one on :8000 with no record) shows as a Single. 5.3's rule (one model id on two nodes = Replicas) is gone: Replicas, Split and Role are records, and the fleet update and the `version-mismatch` rule read them (its detail names the Replicas and Splits whose members run more than one release). `single` and `role` have one member, `replicas` two or more on one release (409 `version_mismatch` otherwise), `split` 2 or 4 with one stage each in member order; `role_of` is another record. A member is resolved to its node's engine (409 `no_engine`, `ambiguous_engine` with more than one: name it) and the backend that reaches it; one the engine has none of is made (`http://<node address>:<port>/v1`). A member's `state` is `serving` (its backend answers and, after a start, a move or a rejoin, one token came back), `starting`, `down`, `draining` (its node is drained), `leaving` (a move takes it out), `mismatch` (a Replicas member on another release, or with other weights, than the first serving one; or, SRV-741, whose identity block differs in a field other than `max_len`, or whose output canary gave other tokens), `off` or `gone`; only `serving` is `routable`. `status` is `serving` when every member serves, `degraded` when some do, `starting`, `down`, or `stopped` when `state` says so; a Split is `stopped` (planned and recorded) until ENG-307. `POST`, `PATCH` and `DELETE` and the actions need what the other writes need. A `PATCH` or `DELETE` while a job runs is 409 `busy`.
- The gateway (SRV-731): `/v1/models` lists each deployment once, a record under its `api_id` (`owned_by` `fleet`, `tandem.deployment`, `tandem.nodes`), then the backends' models no record covers. A request for a record's `api_id` (or its id) goes to its members: a Replicas conversation to its home (the engine's own conversation key; the member that answered keeps it), a new one by rendezvous hash, one without a key to the member with the fewest in flight; the other serving members are its fallbacks before the backend's own. Every answer from a node's engine carries `X-Tandem-Node` (the node's alias) and `X-Tandem-Deployment`; the ledger row `node` (the id) and `deployment`. A drained node is never first and takes no new conversation; with no other member the client gets 503 `node_draining`. A constrained request (`structured_outputs`, a non-text `response_format`, a grammar or guided field, a forced `tool_choice`) moves on only when the first member never took it. A stopped deployment answers 503 `deployment_stopped`, a Split 501 `not_built`.
- Deployment actions (SRV-731): `start` starts each member's engine through its agent (409 `not_managed` for one TandemNode did not start that does not answer), waits for its health and one token (the warm-up); a Split's start is 501 `not_built` until ENG-307. `stop` (destructive: the plan's `confirm`, single use, five minutes, 428 without, 409 `confirm_invalid`) turns the record `stopped` first, lets what is in flight finish (600 s at most), then stops each engine; `move` (`from`, `to`, `engine?`; destructive) starts and warms the engine on `to`, adds it, turns `from` `leaving`, lets its requests finish, stops its engine (one TandemNode does not manage keeps running, said in the job) and drops it: the API id stays. One job per deployment; a controller that stops during one marks it `failed` (`interrupted`) at its next start. Timeouts: an engine's start 1800 s, the health and warm-up 300 s, the requests in flight 600 s; a fleet update's rejoin waits 300 s for its engines up and its deployments warm.
- The placement planner (SRV-731, `proxy/placement.py`): each node (or each of `nodes`, in order) is planned from its own estimate, the engine's Setup Guide formula with that node's device and MemAvailable, read over HTTP only: `POST /node/setup/estimate`, which its TandemNode agent relays to its engine's `POST /v1/setup/estimate`, and for the controller's own machine read without its agent that machine's engine's `POST /v1/setup/estimate` (`source` `engine`). A node whose engine is absent or does not answer has no estimate (`source` `none`, `reason` `<alias> has no estimate: ...`) and fits nothing. The `source` values `agent` (TandemNode's own copy of the formula) and `process` (the controller's, in-process) stay in the schema (v1 is additive) and are no longer produced: neither TandemNode nor the controller computes an estimate; only an older TandemNode that still computes one answers `agent`. A node that serves nothing fits when the estimate fits its budget; one that serves something keeps it, so the new engine's parts (the total less the OS) and the floor must fit in what is free now: `needs 98 GiB, Gold has 61 free`. `single` and `role` need one node that fits, `replicas` two on one release (`warn` when one is tunnelled and one is on the LAN), `split` 2 or 4 nodes each joined to the next by a fabric link (their ConnectX interfaces up in one subnet, from the agents' link-test info), one release and each stage's share fitting (the weights and the KV divided, the rest whole): `no fabric link between Gold and R-1`. A Split's `built` is false: planned and recorded only.
- The weights (SRV-731, `proxy/fleetweights.py`, `proxy/nodeweights.py`): a node's packs are its agent's (the Setup Guide's and its weights store's), each with its content id (sha256 over the names, sizes and sha256s `_hub_manifest.json` records). A copy (one per receiving node at a time; 409 `busy`) opens a receive on the receiver (409 `exists` when the pack is there, 507 `no_space` without its size and 1 GiB free), sends each file hashed on both ends (`direct` from the source's agent when both nodes are paired over mTLS on the LAN, each pinned on the other first; `relay` through the controller otherwise), commits, and is `verified` when the copy's content id is the source's (or, for a pack without a hub manifest, the id of the hashes the sender read). A failed or stopped copy leaves nothing on the receiver. A removal needs its plan's `confirm` (428, 409 `confirm_invalid`) and is refused 409 `in_use` while a deployment that is not stopped serves that pack on that node. Copies and removals are `weights` events and need what the other writes need.
- A Replicas member's `check` (SRV-741, `proxy/canary.py`): `identity` (`read`, `pending`, `failed`, `not_available` for an engine before engine API 1.1, `mismatch`), `identity_text`, `field` (the first identity field that differs), `window` (the engine's `max_len`), `canary` (`pass`, `mismatch`, `near_tie`, or null before a round), `canary_text`, `canary_at`. A `near_tie` is a warning in the deployment's `warn`; the member serves. A request whose prompt and `max_tokens` exceed every member's window when the windows differ is 400 `context_length_exceeded`.
- v1.0, the deployments behind one API (SRV-731): `/v1/fleet/deployments` and its routes, `/v1/fleet/placement`, `/v1/fleet/weights` and its routes; a deployment's `record`, `state`, `managed`, `member_states`, `job` and `affinity`; the error types `no_engine`, `ambiguous_engine`, `not_managed`, `busy`, `in_use`, `exists`, `no_space`, `deployment_stopped`.
- Each node's Setup Guide through the controller (VIS-252, `proxy/fleetsetup.py`): `GET` and `POST /v1/fleet/nodes/{id}/setup/<route>` is that node's engine's `/v1/setup/<route>` as its TandemNode agent relays it (`/node/setup/<route>`, `POST estimate` included: the agent answers 503 `no_engine` when no engine there serves the guide and `engine_down` when it does not answer; the controller's own machine read without its agent: its engine's route). The answers, an event stream included (a job's log with `Last-Event-ID`, Wren's answer), are the Setup Guide's contract unchanged (`docs/setup.md`, `dashboard/src/api/types.ts` `Setup*`, errors `{type, code, message}`); so is the refusal of a POST that is not a same-origin JSON request (`json_only`, `cross_site`, `cross_origin`) and of another method (405 `method_not_allowed`). The relay's own refusals are fleet errors: 404 for a node the fleet does not have, 503 `unreachable` (the node does not answer) or `no_engine`, 502 `unreachable` (its agent dropped the call), 428 `confirm_required` and 409 `confirm_invalid`. Every route needs what the engine's own `/v1/setup` needs (the `setup` rule: open while no admin password is set, else the password, a session or the controller's machine). The writes, `apply`, `remove`, `reset`, `jobs/<id>/retry` and `assistant/load`, need the confirm of their plan (`setup-confirm`): single use, five minutes, for that node, that route and what the plan was read for (apply: `model` and `profile` of the selection; remove: `profiles`, comma-separated; reset: `level`), so the body sent must name the same; a dry run is a read. A plan is `allowed` false with `blocked` in words for a node that does not answer, and for a removal of a pack a deployment that is not stopped serves there. A write the node took is an `engine` event (`Setup Guide on Gold: apply qwen3.8-27b/exl3-4.0`, `by` who).
